# Phase R1 Vendor Documentation and Test-Asset Findings

## Texas Instruments modem DSP application book

Source: Tim Massey and Ramesh Iyer, *DSP Solutions for Telephony and Data/Facsimile Modems*, Texas Instruments SPRA073, January 1997.

This is an unusually useful vendor application book because its modem half is organized around the exact implementation blocks needed later in AndroidDialup:

- modulation methods
- data scrambling
- trellis coding
- V.34 line probing
- point selection
- V.34 framing
- nonlinear precoding
- pulse shaping
- echo cancellation
- fast echo-canceller training
- QAM demodulation
- clock recovery
- adaptive equalization
- equalizer training and decision-directed adaptation

The book also explains V.34 as a multi-phase startup process. Its implementation discussion supports the architectural decision that V.34 should not be attempted until V.8, timing/carrier recovery, equalization and echo-cancellation infrastructure is proven independently.

Notable V.34 implementation notes from the TI source:
- V.8 feature negotiation uses V.21 300-bit/s FSK.
- Phase 2 uses A/A~ and B/B~ tone reversals for round-trip delay estimation and line-probing signals L1/L2 for channel characterization.
- Later training uses PP and TRN sequences for equalizer training/refinement.
- Echo canceller, QAM demodulator, clock recovery and adaptive equalizer are treated as distinct receiver subsystems rather than one monolithic demodulator.

Reuse classification: REFERENCE ONLY. This is vendor explanatory material, not code licensed for direct inclusion.

## Rockwell historical data book

A 1987 Rockwell Modem Products Data Book was located through Bitsavers. The indexed table of contents includes discrete data-pump products for 4800/9600/14400 bit/s service and V.32-class parts such as R9696DP/R1496MM. Direct automated PDF retrieval from Bitsavers was blocked during this research pass, so no detailed page-level implementation claims are being recorded yet.

Status: SOURCE LOCATED / CONTENT REVIEW PENDING.

Use when accessible for:
- historical data-pump architecture
- host/data-pump partitioning
- line-interface assumptions
- training/debug metrics
- register and control-plane behavior

## `cryan209/v90modem` repository

Repository discovered during source archaeology. It contains substantial modem-oriented material, including:
- `clock_recovery.c/.h`
- `data_interface.c/.h`
- call-init/tone probing code
- bundled SpanDSP trees
- an `ITU Docs` directory
- `.tmp_v32bis_startup.wav`
- `USR_V90_VEverything_44000k23600k.wav`

The V.90 WAV filename strongly suggests a USRobotics V.Everything capture with 44,000-bit/s downstream / 23,600-bit/s upstream connection context, but that interpretation is not considered verified until provenance/metadata is documented.

### Licensing finding

A repository-wide license search found licensing notices inside bundled third-party projects such as SpanDSP, but did not establish a clear top-level license for the repository's original code or WAV assets. Therefore:

- do not copy original source into AndroidDialup;
- do not redistribute its WAV files yet;
- use the repository only as a research lead until ownership/license/provenance is established;
- locally generated measurements of publicly accessible material may inform independent implementation, but test assets committed to AndroidDialup require clear redistribution rights or must be regenerated independently.

Classification: REFERENCE / TEST-ASSET LEAD ONLY.

## Test-vector strategy refined

The regression suite should contain at least four provenance classes:

1. **Standard-derived synthetic vectors**
   Generated independently from constants/state machines specified by ITU documents.

2. **Independent open-source vectors**
   Generated by a separately maintained implementation such as minimodem or SpanDSP. Store the generator version, command line and license metadata.

3. **Hardware captures**
   Record real modem audio ourselves using known modem models and negotiated modes. These will become the strongest practical interoperability fixtures because we control provenance and can preserve exact capture conditions.

4. **Third-party historical captures**
   Reference externally hosted recordings when useful, but only mirror them into this repository after redistribution rights are verified.

Every committed WAV/PCM/bitstream test asset must have adjacent metadata recording:
- source/generator
- exact version or hardware model/firmware
- calling vs answering role
- negotiated modulation/rate
- sample format/rate
- capture chain
- expected decoder result
- license/provenance
- SHA-256

## Phase R1 hardware-capture recommendation

For the first lab fixture use two independent modem endpoints if available, or one hardware modem plus SpanDSP/minimodem where applicable. Capture both directions separately at 8 kHz and at a higher archival sample rate such as 48 kHz. Initial target captures:

- V.21/Bell-103-class low-speed call
- V.22bis 1200 and 2400 startup/training
- V.32bis startup/retrain if hardware permits
- V.34 negotiation/training
- V.90 connection if a digital-side/PSTN-capable test arrangement becomes available

These captures should feed both DSP regression tests and the PCM/VBD network-impairment simulator.
