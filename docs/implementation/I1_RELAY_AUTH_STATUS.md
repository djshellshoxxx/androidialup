# I1 Relay Authentication Status

Status: GREEN checkpoint (Python reference); Android port pending

## Summary

The relay no longer accepts the literal `test-proof` string against a fixed
nonce. The Python reference now implements the Beta per-device credential
method named in `docs/spec/S1_WIRE_PROTOCOL.md` section 4.1:

```text
method = "device-credential-hmac-sha256-v1"
```

The wire format of `AUTH_BEGIN`, `AUTH_CHALLENGE`, `AUTH_RESPONSE`,
`AUTH_OK` and `AUTH_FAIL` is unchanged; only the contents of `nonce`,
`method` and `proof` are now defined.

Code:

- `prototype/python/androidialup_relay/auth.py` (new): transcript, proof,
  credential store protocol, per-session authenticator.
- `prototype/python/androidialup_relay/session.py`: takes an `authenticator`.
- `prototype/python/androidialup_relay/server.py`: takes a
  `credential_store`; closes the connection after flushing `AUTH_FAIL`.
- `prototype/python/androidialup_modem/relay_port.py`: takes a
  `device_secret`; raises `RelayAuthenticationError` on `AUTH_FAIL`.
- `prototype/python/tests/test_relay_auth.py` (new): 32 tests.

## Flow

```text
client                                   relay
  HELLO(endpoint_id) ---------------------->
  <---------------------- HELLO_ACK(relay_id)
  AUTH_BEGIN ------------------------------>
  <----------- AUTH_CHALLENGE(nonce, method)   nonce = 32 random bytes per session
  proof = HMAC(...)                            relay remembers (nonce, endpoint_id, relay_id)
  AUTH_RESPONSE(proof) -------------------->
  <-------------- AUTH_OK(endpoint_id, policy) on match
  <-------------- AUTH_FAIL("authentication failed") then TCP close otherwise
```

## Exact proof definition (port this byte-for-byte)

```text
proof = HMAC-SHA256(key = device_secret, message = transcript)

transcript =
    "ADUP-AUTH-v1"                       12 ASCII bytes, NO length prefix
 || u16be(len(relay_id_utf8))            2 bytes, big-endian
 || relay_id_utf8                        relay_id from HELLO_ACK, UTF-8
 || u16be(len(nonce))                    2 bytes, big-endian
 || nonce                                from AUTH_CHALLENGE; 16..65535 bytes
 || endpoint_id                          exactly 32 raw bytes, as sent in HELLO
```

Rules:

- `device_secret` is an opaque byte string, at least 1 byte; provision 32
  random bytes.
- `relay_id` is the UTF-8 string the relay sent in `HELLO_ACK`, used verbatim.
  A proof for one relay therefore fails against any relay with a different id.
- The nonce is generated by the relay with a CSPRNG, 32 bytes by default. A
  client must refuse a nonce shorter than 16 bytes (`ProtocolError`).
- The proof is the full 32-byte HMAC-SHA256 digest, sent raw in
  `AUTH_RESPONSE.proof`.
- The relay compares with a constant-time comparison and consumes the pending
  nonce on the first `AUTH_RESPONSE` whether it matched or not. A second
  `AUTH_RESPONSE`, a replayed proof, a proof for another endpoint, a proof for
  another relay, an unknown `endpoint_id` and a wrong secret all produce the
  same `AUTH_FAIL("authentication failed")`.
- A client must check `AUTH_CHALLENGE.method` equals the string above before
  computing anything and must raise `ProtocolError` otherwise (no proof is
  sent).

```java
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(new SecretKeySpec(deviceSecret, "HmacSHA256"));
mac.update("ADUP-AUTH-v1".getBytes(StandardCharsets.US_ASCII));
byte[] relay = relayId.getBytes(StandardCharsets.UTF_8);
mac.update((byte) (relay.length >>> 8)); mac.update((byte) relay.length); mac.update(relay);
mac.update((byte) (nonce.length >>> 8)); mac.update((byte) nonce.length); mac.update(nonce);
mac.update(endpointId); // 32 bytes
byte[] proof = mac.doFinal();
```

## Provisioning assumptions (Beta)

- Each device has a 32-byte `endpoint_id` (sent in `HELLO`) and a secret
  known only to that device and the relay. Enrolment is out of band for I1.
- The relay keeps an `endpoint_id -> secret` table behind the
  `DeviceCredentialStore` protocol. The reference provides
  `InMemoryDeviceCredentialStore`; a file- or database-backed store is a
  drop-in replacement.
- By default `RelaySession` and `RelayTcpServer` start with an empty store,
  so an unprovisioned relay authenticates nobody.
- Authentication success is independent from TLS server authentication: the
  TLS layer authenticates the relay to the device; this exchange authenticates
  the device to the relay.

## Security notes

- Secrets and proofs never appear in `repr`/`str` of the store, authenticator
  or `RelaySessionPort`, nor in `AUTH_FAIL` reasons or exception text (tested).
- The relay does not reveal whether an `endpoint_id` is enrolled: the MAC is
  computed on a dummy key for unknown endpoints and the failure text is
  identical.
- Nonce freshness is per TLS session; a captured `AUTH_RESPONSE` is useless
  after the session that issued the nonce has consumed it.
- Mutual TLS is not required by this method; the device proves possession of
  the secret inside the already-authenticated TLS tunnel.
